# 排障方法论（P254 修订）

## 当前排障循环

先定位“哪一层的哪一个现象”：host 抓屏、guest 启动、UI 首刷、服务或驱动。可同时列出独立阻塞，但每个实验只处理一个；VNC 黑屏与 guest 崩溃不能合并成同一根因。

1. 保存可复现基线：受影响仓 HEAD/未提交差异、有效配置、启动命令、产物哈希、最早异常日志。日志与 ELF 必须成对。
2. 用“观察 O / 假设 H / 实验 E / 结论 C”分开写。历史日志属于前人报告，未重新复现要注明。
3. 至多列 3 个有区分度的假设，选信息增益高、改动最小的一项。代码少不等于实验好：关闭整个 syslog 会降低观测能力。
4. 一次只变一个因素，写出支持/不支持时各预期什么；重建并核实实际运行了新产物。一次结果不能排除整个模块。
5. 连续 2 次无新信息，停止加补丁，汇总已知/未知与有效性缺口。回查构建身份、诊断手段或请求缺失信息；“换个名字继续猜”不算换方向。
6. 失败实验只撤销自己的变更；已有用户改动先存差异再分组确认。每轮新增补丁必须标明保留/撤销/待审，不让诊断状态成为默认产品状态。

### 实验记录模板

```text
E编号 / 日期 / 平台：
O：确切现象、最早异常、原始证据位置
基线：仓 HEAD + dirty diff；配置/ELF 哈希；启动命令
H：待验证解释（不是根因）
唯一变量：具体函数/配置；其他条件如何保持相同
预测：若 H 成立/不成立，分别应观察到什么
结果：退出码、关键输出、证据路径；未运行则写未运行
C：支持/削弱/无效实验；只能说明什么、仍未知什么
补丁去留：保留/撤销/待审及原因
下一步：仅一个，包含成功与失败分支
```

“关闭 KASAN 后仍崩”仅表明该构建下关闭它未消除崩溃；“栈扩大仍崩”不证明没有越界；异常落在锁函数里不证明该函数是最早破坏者。只有捕获写入者/越界现场等直接证据，或可重复的单变量修复与恢复对照，才可升级为根因结论。

## 历史经验（按适用范围使用）

> 来自切歌无声排查 + 音乐后台化 + 代码审计的经验，写的是**处理方式**不是本次记录。
> **本文件不是每次会话必读，排障时按需加载。**

1. **寄存器差异定位法**：对比"正常路径 vs 异常路径"的全部寄存器，锁定唯一差异位 → 但差异位可能是**果不是因**（例：bit30 是 Ramp Rise 完成中断标志，不是病因）。先确认差异位的**属性**再动手改。
2. **写不进 ≠ 代码没执行**：同寄存器其他位能写、某位写不进 → 先查手册确认该位是 R/W / R/W1C / 只读。R/W1C 位**写 1 是清除中断**、置位权在硬件，软件无法伪造。
3. **手册优先**：全志芯片寄存器语义一律以官方 User Manual 为准（R528 UM 已下载 `/tmp/R528_UM.pdf`，`pdftotext -layout` 可查）；驱动头文件注释可能不完整。
4. **状态机生命周期**：使能位 ≠ 状态机复位。RD_EN 只是 gate，Ramp FSM 需要 close 时显式 `RAMP_SRST(bit24)` 软复位脉冲（置 1→延时→清 0）才能下次重新 Rise——**关外设要关状态机，不只关使能**。
5. **POWER 类寄存器禁止整写**：POWER_ANA_CTL 只受系统总线控制、ALDO_EN 关联整个模拟域——只可 `update_bits()` 局部操作，`write()` 整写会殃及屏幕等（曾屏闪/黑屏）。
6. **后台化生命周期四问**（UI 与服务解耦时）：①对象删除前是否已清所有指针引用（先 clear 再 del）②常驻 timer 回调是否判空 ③状态是否有唯一来源（单线程修改）④实例是否可能双开（create 前必 destroy 旧）。
7. **死代码防护**：为未来架构预留的模块若未接入，必须**不进 Makefile 编译** + 头部 TODO 注释说明接入前置条件——防后续会话误调用产生第二个实例/双状态源。
8. **改动顺序**：先跑通 → 稳定 → 抽象，不要架构先行；嵌入式最怕"架构漂亮但板子不能跑"。
9. **审计六查**：唯一性 / timer 生命周期 / UI 对象生命周期 / 状态唯一来源 / 创建删除平衡 / 真实调用链图 + TOP 风险——交付前自查清单。
10. **测试三档**：正常连播 2h / 疯狂切界面 100 次 / 异常场景（拔卡、坏文件、下一曲损坏）——异常档最易暴露问题。

## 子 APP 改造 / DEBUG 标准流程（SOP，2026-09-11 沉淀）

> 触发：改 `luncher_dm` 下某一页（`ui_*.c`）的需求改动 / DEBUG / 交互重做。
> **一律按本流程，禁止读一半就动手**（日历页连改数轮才对齐 = 反面教材）。AGENTS.md §〇-4 指针指向本节。

1. **读代码**：定位对应 `ui_*.c` + `deskmate_ui.h` 宏/构建器 + 相关服务层，通读现状与调用链，再下结论。
2. **分析结果**：拆成「UI 表现 / 交互逻辑 / 数据逻辑 / 生命周期」四类，逐条列问题与根因，区分表象与真根因。
3. **评估可行功能**：每个问题给 1~N 个方案，**先查 LVGL 是否支持**（`lv_obj_scroll.h` / `lv_anim.h` / `lv_event.h` 等），标注改动量/风险；LVGL 做不到就不设计（deskmate-ui 铁律3）。
4. **处理决策**：用户已明确授权的修复/实现直接进行；仅产品交互取舍、范围变更、缺失外部信息或破坏性操作需要确认。只读审查、保存证据、提出最小实验无需反复询问。
5. **再改代码**：按确认方案实现，遵守代码风格（禁乱加注释）；改完自查（括号平衡 / 无残留旧符号 / 无 warning）。
6. **汇总报告**：列改动文件、证据、遗留项和待验证点；按 [开发流程](specs/misc/development-workflow.md) 区分模拟器、板端和文档任务，编译不等于运行通过。

## 思维模型：四层排查法

你必须严格按照这个顺序排查，**不允许跳层**。

### 第一层：静态分析（不烧录、不运行）

在你请求用户做任何操作之前，先回答以下问题：

1. **这个函数的输入是什么？输出应该是什么？**（函数签名、参数、返回值）
2. **这个函数的控制流有多少条路径？**（列出所有 if/else/switch case）
3. **这个函数的时序依赖是什么？**（是否需要先调用某个初始化？是否有锁？是否依赖中断？）
4. **这个函数在第一次调用和第二次调用时有什么不同？**（全局状态、静态变量、硬件寄存器）

**纪律：** 没读完相关函数的所有分支之前，不提出任何假设。

### 第二层：寄存器级诊断（一次烧录，全面取证）

当你需要用户烧录固件时，确保这一次烧录能回答**所有**未解问题。

1. **确定需要读取的寄存器清单：**
   - TWI 状态机寄存器（STAT、CTL、CLK、SRST、ADDR）
   - CCU 时钟门控寄存器
   - CCU 复位控制寄存器
   - GIC 中断使能寄存器
   - GPIO 数据寄存器（验证 pinmux 和电平）

2. **确定插入诊断代码的位置：**
   - 必须在**故障发生的精确时刻**读取寄存器，不是在错误处理之后
   - 对于 `twi_start()` 超时问题，诊断代码必须插入在 `twi_start()` 函数**内部**（超时发生时立即读取）

3. **验证诊断输出：**
   - 每个寄存器的值必须在你预期范围内
   - 如果某个寄存器值不合理（如全 0 或全 F），这是新的线索

**纪律：** 不要分多次烧录来加诊断。一次性加够。

### 第三层：差异分析

对比"第一次成功"和"第二次失败"之间的所有差异：

```
第一次调用 (成功):                 第二次调用 (失败):
─────────────────────────────     ─────────────────────────────
调用栈:                          调用栈:
  gt911_control_initialize()        gt911_worker()
  → gt911_i2c_read(0x8140)         → gt911_i2c_read(0x814E)
  → r528_transfer()                 → r528_transfer()

系统上下文:                       系统上下文:
  CPU1, 启动早期                    HPWORK（可能是 CPU0 或 CPU1）
  单任务执行                        与其他 init 任务并发
  TWI 第一次 init（全流程）          TWI already_init（仅检查 pinmux）

已确认相同的:                      已确认不同的:
  TWI 基地址 ✓                     调用栈（函数 caller）
  I2C 地址 0x5D ✓                  寄存器地址（0x8140 vs 0x814E）
  频率 100KHz ✓                    数据长度（4 bytes vs 1 byte）
  BUSEN=1 ✓                       调用上下文（线程 vs work queue）
```

**纪律：** 不要假设"相同代码路径就应该产生相同结果"。找出所有差异点，逐一排除。

### 第四层：假设验证与排除

每个假设必须满足以下格式：

```
假设：_________________________________________
可验证的预测：如果假设成立，那么我应该看到_______
验证方法：_____________________________________
```

**好的假设示例：**
- 假设：`twi_soft_reset()` 清除了 BUSEN。
- 预测：在 `twi_start()` 之前读 CTL 寄存器会看到 BUSEN=0。
- 验证：在 `twi_start()` 内部、`twi_set_start()` 之前加 `readl(CTL_REG)`。

**坏的假设示例：**
- "可能是时钟问题。"（太模糊，没有可验证的预测）
- "可能是中断没配好。"（没有说明应该看到什么）

**纪律：** 无法用寄存器值验证的假设，不算是假设，只是猜。

## 心态纪律

### 规则 1: 一次只改一个变量

每次修改只能改变**一个**东西。同时改多个东西，你不知道哪个有效。

- ❌ 同时改了 `hal_twi_set_freq()` + `twi_enable()` → 如果问题解决，不知道是哪个起效
- ✅ 先加 `twi_enable()` 在 soft reset 后，单独验证 → 如果无效，再尝试下一个

### 规则 2: 不要相信"修复了"直到你看到证据

- ❌ "这个应该修复了，烧录试试看。"
- ✅ "诊断显示 STAT=0x08（START 已发送），说明 `twi_start()` 现在成功了。但还需要验证完整传输是否正常。"

### 规则 3: 根因必须可以用一句话说清楚

如果你不能用一句话说清楚根因，你还没找到它。

- ✅ "`hal_twi_engine_do_xfer()` 中的 `twi_soft_reset()` 将 TWI 内部状态机复位到 idle，但 CCU 的 TWI0 时钟门控在 NAND 初始化时被意外关闭了，导致 TWI 无法生成 START 条件。"
- ❌ "可能是各种初始化顺序问题、中断配置、或者上拉电阻……"（没找到根因）

### 规则 4: 不要被噪声分散注意力

这个系统中同时运行了很多东西：NAND 初始化、LCD 初始化、传感器（SHTC3、sgp30）、WiFi/BT。这些**都有可能**影响 TWI。

但你的责任是**先证明 TWI 本身的行为**。用寄存器值证明 TWI 控制器收到了正确的指令、有正确的时钟、没有被复位。只有排除了 TWI 本身的问题后，才开始调查外部干扰。

### 规则 5: 永远追问"为什么"

每当你发现一个事实，追问它"为什么"。

- 事实：`stat=0xF8`（空闲）
- 为什么？因为 `twi_start()` 失败了，错误路径做了第二次 soft reset 回到空闲
- 那为什么 `twi_start()` 失败？因为 STA 位在 255 次轮询后没清除
- 那为什么 STA 位不清除？因为硬件没生成 START 条件
- 那为什么硬件没生成 START？因为……
- （到这里你才真正开始找根因）

## 第 5 轮教训（2026-07-25）

### 教训 1: 诊断代码要放在编译器一定会重编的位置

`hal_twi.c` 属于 HAL 静态库（`librtos-hal.a`），增量编译 `m nsh` **可能不重编它**。即使源文件改了对，二进制里也可能没有你的代码。**永远把诊断放在 NuttX 内核文件中**（如 `drv_twi.c`），这些文件每次 `m nsh` 都会重编。

验证方法：编译后 `strings 镜像 | grep -c '你的诊断字符串'`。

### 教训 2: 在 HAL 层用 `printf()` 前确认已 `#include <stdio.h>`

`hal_twi.c` 只 include 了 `<hal_log.h>`，没有 `<stdio.h>`。`printf()` 可能未声明，导致调用异常但编译器不报错。

### 教训 3: 第一轮诊断没触发本身就是数据

我在 `twi_start()` 内部加了失败路径诊断，它没触发。这个"没触发"本身推翻了之前 4 轮的结论——START 条件**确实生成了**。"排除法"的结果和"寄存器快照"的结果一样有价值。

## 第 6 轮教训（2026-07-25）

### 教训 4: 不要轻易否定已验证的数据

第5轮已验证 GICD 物理基址 `0x03001000`。我看到内存映射注释的笔误（"GIC at 0x0302:0000-0x0301:ffff" 结束地址小于起始地址）就把基址改成 `0x03020000`，**浪费了两轮烧录**。

**规则：** 内存映射注释是参考，`readl()` 读到一个已知外设的 ID 寄存器才是黄金标准。如果前人已通过实际读寄存器验证了地址，不要轻易推翻。

### 教训 5: CCU 复位极性可能和你想的不一样

本平台的 `ccu_reset_assert()` 清除 bit（写 0），`ccu_reset_deassert()` 设置 bit（写 1）——**低电平有效**。和常见的"写 1 断言复位"相反。`ccu_reset_reset()` 先 assert 后 deassert（先清 0 再置 1）。

`ccu_reset_status()` 的文档注释直接写着：`return !(map->bit & readl(...))` ——"the opposite of what our hardware uses"。

**规则：** 读复位寄存器的数据前，先看 `assert`/`deassert` 函数的实现，确认极性和文档是否一致。

### 教训 6: GICD 虚拟地址 ≠ 物理地址，要加偏移

NuttX 通过宏 `MPCORE_ICD_VBASE` 访问 GIC 分发器：
```
MPCORE_ICD_VBASE = CHIP_MPCORE_VBASE + MPCORE_ICD_OFFSET
                 = R528_GIC_VADDR(0x03020000) + 0x1000
                 = 0x03021000
```
诊断代码如果直接读物理地址 `0x03001000`（其实是 CCU 的地址），会读到完全不同的数据——之前的"GIC EN=0"结论全是误判。

**规则：** 在 NuttX 内核中诊断中断状态时，永远使用 `MPCORE_ICD_VBASE` 对应的虚拟地址（`R528_GIC_VADDR + 0x1000`），不要直接硬编码物理地址。

### 已排除的假设（第 6 轮）

经过 GIC 寄存器验证、CCU 寄存器验证、TWI 状态机验证，以下假设已被排除：

| # | 假设 | 验证方法 | 结论 |
|---|------|---------|------|
| 1 | GIC IRQ41 被意外关闭 | `readl(0x03021104)` bit9 恒为 1 | ❌ 排除 |
| 2 | CCU TWI0 时钟被关闭 | `readl(0x0200191C)` bit0 恒为 1 | ❌ 排除 |
| 3 | CCU TWI0 复位被断言 | `readl(0x0200191C)` bit16 恒为 1（active-LOW deasserted） | ❌ 排除 |
| 4 | TWI 未生成 START | `twi_start()` 诊断从未触发 | ❌ 排除 |
| 5 | BUSEN 被 soft reset 清除 | CTL(busen=1) 已验证 | ❌ 排除 |

### 当前状态

问题出在 **TWI 控制器产生 START 但不产生中断**。具体原因未知——`twi_enable_irq()` 试图设置 INTEN，但：
- `hal_twi.c` 的 HAL 层诊断输出不可靠（printf 可能不路由到控制台）
- 从 `drv_twi.c` 的 `PRE_XFER` 诊断可以看到传输前 CTL 状态，但传输过程的 INTEN/INTFLG 状态未知

如需继续，下一步应该是：
1. 让用户烧录含 `PRE_XFER` 诊断的固件（已编译好）
2. 看每次传输前的 INTEN/INTFLG 状态
3. 如果传输前 INTEN=1（上次遗留），说明 `twi_disable_irq` 没清干净
4. 如果传输前 INTEN=0（正常），说明 `twi_enable_irq` 设置了但硬件没响应

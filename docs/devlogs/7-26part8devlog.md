## 第一部分：思维操作系统 — 四层排查引擎

这是你调试任何硬件/驱动问题的**默认启动路径**。严格按照这个顺序执行，**不允许跳层**。
每一层回答上一层的疑问，每一层为下一层提供弹药。

```
                    ┌──────────────────┐
                    │  问题描述 / 现象  │
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐

              │     │  (读代码, 不烧录) │

              │     ┌────────▼─────────┐

              │     ┌────────▼─────────┐

              │     │  (好 vs 坏对比)   │
```

### L1 — 静态分析（不烧录、不运行）

在请求任何人做任何操作之前，先回答以下四个问题：

**Q1: 这个函数的输入是什么？输出应该是什么？**
- 函数签名、参数、返回值、副作用
- 特别关注：`NULL` 是否可能？边界值是什么？错误码如何传播？

**Q2: 这个函数的控制流有多少条路径？**
- 列出所有 `if/else/switch/case` 分支
- 每个分支是 error path 还是正常路径？
- 有没有分支从没被执行过？

**Q3: 这个函数的时序依赖是什么？**
- 是否需要先调用某个初始化函数？
- 是否有锁/mutex/semaphore？
- 是否依赖中断（IRQ handler 在哪个 CPU？）
- 第一次调用 vs 第二次调用有什么区别？

**Q4: 全局状态在每次调用时有什么不同？**
- 静态局部变量（`static` inside function）
- 全局变量（尤其是 flag/counter/state machine）
- 硬件寄存器状态（上电默认值 vs 运行中值）
- 调用者上下文（线程 vs workqueue vs ISR）

> **纪律：** 没读完所有相关函数的所有分支之前，不提出任何假设。
> **纪律：** 如果你的分析依赖于"某段代码应该怎样执行"，请去确认它真的在执行。

### L2 — 精确诊断（寄存器级：一次取证，终生使用）

诊断的核心不是"加打印"，是**设计实验**。

#### 2.1 诊断代码的铁律

| 原则 | 说明 |
|------|------|
| **一次到位** | 一次性加够所有诊断，不要分多次烧录 |
| **故障时刻** | 诊断代码插在**故障发生的精确时刻**，不是 error handler 之后 |
| **位置不变性** | 诊断代码不能改变程序的行为（不能加 delay、不能改流程） |
| **自描述输出** | 每行诊断输出必须包含：时间戳 + 函数名 + 行号 + 寄存器名 |
| **编译器验证** | 编译后 `strings 镜像 \| grep -c '你的特征字符串'` 确认诊断存在 |

#### 2.2 诊断优先清单（通用嵌入式）

当遇到"外设不工作"时，按此顺序检查：

```
1. 时钟门控 (CCU / CRG / PRCM)
   → 时钟有没有被关？谁关的？复位默认值是什么？

2. 复位状态 (Reset controller)
   → 外设是否在复位中？复位极性是 active-HIGH 还是 active-LOW？
   → 永远不要信注释，读 assert/deassert 的实现！

3. 中断使能 (GIC / NVIC)
   → 中断号对不对？使能位有没有被意外清掉？
   → 注意：虚拟地址 ≠ 物理地址（NuttX 下尤其如此）

4. 外设状态机
   → 外设的状态寄存器当前值是多少？预期值是多少？
   → 从状态机可以推断出外设在做什么

5. GPIO/Pinmux
   → 引脚功能配置对了吗？电平对不对？
   → pull-up/pull-down 配置是否符合外设要求？
```

#### 2.3 诊断插入位置速查表

| 问题场景 | 最佳诊断位置 | 为什么 |
|----------|-------------|--------|
| 外设超时 | 轮询循环的 `while(count--)` 内部 | 超时发生时立即捕获状态 |
| 中断没触发 | ISR 入口处（第一条指令） | 证明中断确实到了 |
| 数据错误 | DMA 完成回调中、在 memcpy 之前 | 看原始数据 |
| 第一次成功第二次失败 | 函数入口（判别调用次数）和异常路径 | 完整对比 |

> **纪律：** 诊断代码不是功能代码。问题回答完毕，立刻清除。

### L3 — 差异分析（对比的艺术）

问题的最强线索往往不在"哪里错了"，而在于**"什么变了"**。

#### 3.1 差异分析模板

```text
第一次调用 (成功):                 第二次调用 (失败):
─────────────────────────────     ─────────────────────────────
调用栈:                          调用栈:
  函数 A → 函数 B                  函数 C → 函数 D

系统上下文:                       系统上下文:
  CPU 0, 启动早期                  CPU 1, 运行期
  单任务执行                        多任务并发
  外设第一次 init                  外设 already_init

已确认相同的:                      已确认不同的:
  ✓ 基地址                         调用栈
  ✓ I2C 地址                       数据长度
  ✓ 频率                           上下文
  ✓ 配置寄存器
```

#### 3.2 差异分析规则

1. **不要假设"相同代码路径就应该产生相同结果"** — 全局状态可能不同
2. **每个差异点都需要解释** — 无法解释的差异就是下一个突破口
3. **找不同时同时关注"多出来的东西"和"少掉的东西"**
4. **特别关注时间窗口差异**：第一次调用时系统在做什么？第二次调用时又在做什么？

#### 3.3 常见的"看不见"的差异

- 中断优先级：同一个中断在不同上下文中是否被抢占？
- Cache 状态：第一次运行时代码在 cache 里，第二次可能被 evict
- MMU/MPU 配置：页表是否已切换？
- 电源域：某个电源域是否在第一次之后被关闭了？

### L4 — 假设验证（科学的根因锁定法）

#### 4.1 假设格式

每个假设必须写成以下格式，缺一不可：

```
假设：_________________________________________
可验证的预测：如果假设成立，那么我应该看到_______
验证方法：_____________________________________
```

#### 4.2 假设质量检查

| 特征 | ✅ 好假设 | ❌ 坏假设 |
|------|-----------|-----------|
| 具体性 | "`soft_reset()` 清除了 BUSEN" | "可能是时钟问题" |
| 可验证 | "在 `twi_start()` 内部读 CTL 寄存器会看到 BUSEN=0" | "加个 delay 试试" |
| 可证伪 | "如果 BUSEN 没被清除，说明假设不成立" | "这个应该能修好吧" |
| 最小化 | "一个 bit 的改变导致一个特定行为" | "总之就是系统不稳定" |

#### 4.3 假设验证流程

```
假设 → 预测（寄存器值/输出/行为） → 设计验证 → 执行 → 对比预测
   │                                                      │
   └── 匹配 → 假设被证实（验证其他可能性）                 │
   └── 不匹配 → 假设被证伪（排除这个可能性）──────────────┘
                                                    │
                                          缩小搜索范围，继续
```

> **纪律：** 无法用寄存器值验证的假设，不算是假设，只是猜。
> **纪律：** 如果你不能一句话说清楚根因，你还没找到它。

## 第二部分：实战进阶 — 来自战壕的经验

### 2.1 编译器不认识你的意愿

```
❌ "我改了 hal_twi.c，m nsh 应该会重编吧"
✅ "hal_twi.c 在 librtos-hal.a 中，增量编译可能跳过。
    永远把诊断放在每次都会重编的文件中（如 drv_twi.c）。"
✅ "验证方法：strings 镜像 | grep '我的诊断字符串'"
```

**规则：** 编译系统是不可信的。只有 `strings` 输出的证据才是可信的。
**规则：** 输出函数没有 `#include` 头文件（如 HAL 层有 `printf` 但没 `#include <stdio.h>`），编译无错误但运行无输出。每次添加输出前确认头文件。

### 2.2 硬件地址的真相

```
❌ "内存映射注释写 GIC 在 0x03020000"
✅ "readl(GIC 的 ID 寄存器) 返回 0xFC0DEF0B 证明地址正确"
```

**规则：** 注释是参考，`readl()` 读到已知外设的 ID 寄存器是黄金标准。
**规则：** NuttX 中外设地址用虚拟地址，和物理地址有偏移（如 `MPCORE_ICD_VBASE = 实际物理地址 + 偏移`）。**永远用内核提供的宏，不要硬编码。**

### 2.3 复位极性的陷阱

```
❌ "ccu_reset_assert() 应该是写 1 吧"
✅ "ccu_reset_assert() 清除 bit（写 0）——低电平有效"
✅ "ccu_reset_status() 返回 !(map->bit & readl(...)) ——
    文档注释直接写着 'the opposite of what our hardware uses'"
```

**规则：** 读复位/使能寄存器前，先看 `assert`/`deassert`/`enable`/`disable` 函数的实现代码。
**规则：** 文档可能和代码不一致，代码可能和硬件不一致。**以硬件行为为准。**

### 2.4 芯片的行为不需要你理解

```
❌ "为什么 GT9271 第一次读取成功、第二次读取失败？这不合理！"
✅ "有时候问题不在你以为的地方。GT9271 就是要两次重置。"
✅ "这是芯片的特性，不是 bug。Linux 驱动只是恰好 '踩过' 了这个问题。"
```

**规则：** 芯片的行为不需要你的理解，只需要你接受。然后**在正确的层面处理它**。
**规则：** 修复要在最简单的层面上。不要因为芯片行为怪异就去改 HAL 层。

### 2.5 应用层最薄修复原则

当你确认根因在芯片行为/硬件特性/FW 限制时，修复策略按优先级排列：

```
P0: 应用层修复（最薄，最安全）
  → 例：读失败后加 chip reset + retry
  → 优点：不改驱动，不改 HAL，不涉及其他子系统
  → 成本：15 行代码

P1: 驱动层修复
  → 例：驱动 probe 中加 init retry 循环
  → 优点：对应用透明
  → 成本：30 行代码 + 完整的 driver review

P2: HAL/BSP 层修复
  → 例：修改 TWI 驱动时序
  → 优点：全局生效
  → 成本：影响所有 I2C 外设，需要全面回归

P3: 硬件修改
  → 例：改 PCB、加上拉电阻、改电源时序
  → 成本：硬件改版、打样、验证 → **最后的手段**
```

**规则：** 修复层级越深，影响面越大。能用 15 行应用层代码解决的问题，不要动 HAL。

### 2.6 嵌入式 5W1H 追问法

每当你发现一个事实，追问它"为什么/谁/什么时候/在哪里/怎么做"：

```text
事实：stat=0xF8（空闲）
  ↓ 为什么？
因为 twi_start() 失败了，错误路径做了 soft reset 回到空闲
  ↓ 为什么 twi_start() 失败？
因为 STA 位在 255 次轮询后没清除
  ↓ 为什么 STA 位不清除？
因为硬件没生成 START 条件
  ↓ 为什么硬件没生成 START？
因为……（到这里你才真正开始找根因）
```

追踪到第 3-4 层"为什么"之前，你的判断基本是错的。

### 2.7 "第一次能行"陷阱

```
在嵌入式系统中，"第一次能行"是最危险的信号。
它意味着你的代码没问题，但环境有问题。

第一次成功：
  - 上电后外设处于已知状态
  - 系统刚启动，中断/时钟/DMA 还没被别的模块配置过
  - 时序窗口特别宽裕

第二次失败：
  - 外设状态被第一次调用改变了
  - 某个模块配置了共享资源（时钟、中断、DMA）
  - 任务调度导致时序窗口收紧
```

**诊断方法：**
1. 在第一次和第二次调用之间插入 `delay(1000ms)`，如果问题消失 → **时序问题**
2. 在第一次和第二次调用之间插入 dummy I2C 读（读一个无关寄存器），如果问题消失 → **芯片状态问题**
3. 手动调用两次相同的函数（不经过中间状态），如果都成功 → **环境变化问题**

## 第三部分：调试行动协议

### 3.1 调试前 Checklist

```
□ 我已经通读了所有相关代码（至少 3 遍）？
□ 我能画出问题的函数调用链（从应用到硬件）？
□ 我知道每个函数的所有分支路径？
□ 我知道第一次和第二次调用的所有不同？
□ 我的假设可以写成一个"如果 X 那么 Y"的句子？
□ 我可以通过一个寄存器值来验证这个假设？
□ 我知道这次烧录要验证多少个假设？
```

### 3.2 修复后 Checklist

```
□ 我确定修复是针对根因的，不是针对症状的？
□ 我清除了所有诊断代码？
□ 编译后 strings 确认诊断代码已消失？
□ 我可以用一句话说清楚根因？
□ 这个修改是最薄的修复层面吗？
□ 这个修改不会影响其他子系统？
```

### 3.3 挫败处理协议

当你调试了 3 轮以上还没找到根因：

```
1. 退回到 L1：重新通读所有相关代码（你上次可能有遗漏）
2. 确认你的诊断代码确实被执行了（strings + 输出日志）
3. 确认你的诊断代码插入在正确的位置（不是在 error handler 之后）
4. 重新检查所有硬件地址（虚拟 vs 物理，偏移 vs 基址）
5. 寻找"你没想到会变"的东西：电源域、时钟树、中断优先级
6. 再次确认：**这个故障是否 100% 可复现？** 不能复现的问题不要 debug
```

## 第四部分：快速参考 — 常见问题模式

| 症状 | 最可能的根因 | 验证方法 |
|------|-------------|---------|
| 外设第一次工作第二次不工作 | 芯片状态问题 / 共享资源被修改 | 对比两次调用前的寄存器 |
| 外设偶尔不工作 | 时序竞争 / 中断优先级 | 加延迟复现 vs 不复现 |
| 外设完全不工作 | 时钟/复位/电源/引脚 | 读 CCU 时钟门控 + 复位状态 |
| 中断不触发 | 中断使能 / 中断号 / CPU affinity | 读 GIC 使能寄存器 + 确认中断号 |
| Data Abort | 指针错误 / 越界 / 野指针 | 看 abort 时的 PC 值 + LR |
| 编译通过但没效果 | 增量编译跳过 / printf 无头文件 | `strings` 验证 |
| I2C NACK | 地址错误 / 芯片未就绪 / 总线冲突 | 读 TWI 状态机寄存器 |
| 音频无声 | 音量=0 / 功放未使能 / 设备路径错误 | 读 codec 寄存器 + 设备节点存在性 |

## 第五部分：VelaDevPower 格言（记住这些）

1. **"我不是在猜，我是在排除。"** — 每一步都有一个可验证的预测
2. **"不要治疗症状，要找到病原体。"** — 如果一个补丁没解决根因，就不要提交
3. **"代码比日志更重要，寄存器比代码更精确。"** — 读代码，读寄存器，不要依赖猜测
4. **"烧录固件是最后的手段，不是第一步。"** — 先在静态分析中排除 80% 的可能性
5. **"硬件问题用软件修不了，软件问题用硬件也修不了。"** — 先分清是哪一类
6. **"芯片的行为不需要你理解，只需要你接受。"** — 在应用层用最少的代码解决问题
7. **"编译系统是不可信的，strings 输出才是。"** — 确认你的代码真的进了固件
8. **"诊断代码不是功能代码。"** — 回答问题后立刻清除，不留痕迹
9. **"一次只改一个变量。"** — 同时改多个东西，你不知道哪个有效
10. **"如果你不能一句话说清楚根因，你还没找到它。"** — 继续追下去

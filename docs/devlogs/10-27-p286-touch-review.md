# P286 触摸专项复核与 INT 接线更正（2026-10-27）

目标：解释断触与恢复恶化，核对 HX83102B / R528 TWI 实际路径；验收为可追溯发现与下一步观测。
平台：R528 V2；本次仅审查和记录，没有修改驱动、配置、接线，没有编译或刷机。
基线：vendor/allwinnertech HEAD `4c122d896b8ca786ad3f9a6768f37eeecdfe71e8` + 用户已有 dirty 工作树。
独立两路审查：触摸协议/生命周期、TWI 状态机/错误传播；主流程复核以下结论。

## 1. 最新接线事实优先于旧记录

用户本次明确：**RST、SDA、SCL 有 3.3 V ↔ 1.8 V 转换；INT 没有转换，仅有 10 kΩ 上拉到 1.8 V。**
因此参考板记录中“所有信号板端均 3.3 V”的泛化不再适用于当前 INT。
PB5 所属 IO 域供电仍应以板级原理图/实测确认，不能仅由其他三根线高压侧推定。

若 PB5 IO 域为 3.3 V，1.8 V 不满足常见的 0.7×VCCIO 高电平保证条件；
R528 datasheet 搜索索引给出的 GPIO VIH 最低为 0.7×VCCIO（3.3 V 时 2.31 V）。
PDF 完整获取失败，不能把 SDIO 专项门限或别的芯片门限混用到 PB5。
这支持“INT 读低可能是门限不匹配”，尚不证明本次全部断触由 INT 导致。

不建议开启主控内部上拉去凑 2.4 V：外部 10 kΩ 到 1.8 V 与内部上拉到 IO 域构成双电源网络；
内部阻值、模组输出结构与钳位未知，电压不受控，可能向模组或 1.8 V 电源注入电流。
纯电阻、高阻输出假设下，若内部上拉 50 kΩ，计算值仅 2.05 V；这不是 R528 阻值实测。
即使测到 2.4 V，也不能证明满足 HX83102B INT 绝对最大额定值或有足够噪声裕量。
合理方向为 INT 增加适配其输出类型的 1.8→3.3 V 电平转换，分别保留两侧电平。
未获取该模组 INT 开漏/推挽与耐压资料，不把开漏作为已知事实。

当前 worker 仅采样/记录 INT，实际读取由 last_state 和 100/20 ms 定时决定；
因此 INT 电平修正不会自动启用 IRQ 或 INT 门控，也不能保证消除 TWI 错误。

## 2. 确定的源码问题

### F1 / High：STOP 失败被当成功（原有缺陷，未证明为唯一根因）

`hal_twi.c:594` 的 twi_stop 在 STOP/STAT/LCR 超时时返回 SUNXI_TWI_TFAIL=-4；
`:1768` 却只检查 SUNXI_TWI_FAIL=-1，且即便命中也只打印，不修改 err_code。
成功收完数据的路径可能在 STOP 失败后仍通过 engine_complete(twi, 0) 报成功。
修复方向：保存并传播 STOP 错误，明确区分“收到数据”与“事务完整结束”。
对应 L1-4 / P-32。当前没有运行证据证明哪次断触触发了此缺陷。
TWI_ERR 宏在本地源中被禁用，所以现有日志没有 STOP 错误行并不是排除证据。

### F2 / High：恢复失败被过度解释成 SDA 被芯片拉低

`hal_twi.c:1071` 成功条件同时要求 SRST 完成、两线高、STAT=f8；任一不满足均可失败。
`:2961` 等路径将恢复失败统一映射 BUS_STUCK，drv_twi 转 -EBUSY；
`hx83102_iic_touch.c:725` 对 -EBUSY 提前升级恢复，后续可发芯片 RST。
因此 -EBUSY 并不专指 SDA 低，更不证明只能通过芯片 RST 恢复。
修复方向：区分线低、控制器未 idle、SRST 超时，再决定恢复层级。对应 L1-4 / P-32。

## 3. 需要撤回的确定性解释

R2c 仅撤掉 recover 内的前置软复位；`hal_twi_engine_do_xfer():1997` 仍然每笔先软复位，
`:2005` 才调用 recover。不能说整条链已经是“先打时钟、后软复位”。
`hal_twi_set_frequency():2540` 同频直接返回，整个函数没有 twi_enable(BUSEN)。
BUSEN 设置在 clk_init 的 `:2504`；“每次尝试重写分频并使能 BUSEN”不符合当前源码。

是否 SRST 实际清 BUSEN/CLK 仍未知。R2b 日志 16 个 E13 快照的 CTL 为
4c×2、40×7、48×7，bit6 均为 1，CLK 均 5a；这削弱旧解释，但不是复位前后成对测量。
旧文档“已由板子证实软复位清 BUSEN”的结论不能继续作为修复依据。

`ret=0` 仅表示最后一次 HAL 返回成功：HAL 内部可以经历失败、恢复、重试；
触摸 worker 对无效帧再读一次并覆盖 touch_buf，转储只保留末次帧。
加上 F1，不能据 ret=0 排除总线层，也不能从全零直接推定 IC 内部状态丢失。

## 4. Firefly HX83102B 协议差异（待单变量验证）

参考：`/home/<user>/Firefly_SDK/kernel-6.1/drivers/input/touchscreen/hxchipset/`。

1. incell_core.c:1590：写 **0x11=0 → 读 0x30 → 写 0x11=1**。
   常量见 ic_core.h:301；HX83102.c:1693 的 AB 分支沿用此回调，只有 E 型覆盖为直接读。
   本地 worker:666/683 直接读 0x30；0x13/0x0d 桥配置并不等于 0x11 操作。
2. common.c:1678 在 reset 后读 128 字节，:1942 丢弃 reset 后首帧；本地仍直接读 56。
3. common.c:1773 检查 f[52] 高半字节 raw_out_sel，模式不符时清剩余 72 字节；
   本地 decoder 只用低半字节点数，没有对应处理。

这些是已核实的移植差异，不是已证实的断触根因。F101 简化直接读能够工作，
也不支持“一缺 0x11 就必然失败”的断言。Firefly transport 本身会立即重试整笔 I2C，
不能泛称所有立即重试都会破坏事件栈。

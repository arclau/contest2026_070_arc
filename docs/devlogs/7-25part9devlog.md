# MiuMiu 思考方式 — GT9271 触摸修复 + LVGL Demo 调试方法论

> 本文档定义了本阶段调试中采用的**思维方式**和**推理纪律**。核心教训：有时候问题不在你以为的地方。

## 核心信条

- **"我不是在猜，我是在排除。"** 每一步都有一个可验证的预测。
- **"不要治疗症状，要找到病原体。"** 如果一个补丁没解决根因，就不要提交。
- **"硬件问题用软件修不了，软件问题用硬件也修不了。"** 先分清是哪一类。
- **"芯片的行为不需要你理解，只需要你接受。"** GT9271 就是要两次重置，没有为什么。

## 思维模型：三层定位法

### 第一层：区分"驱动问题"还是"芯片问题"

当 I2C 读取失败时，先问：**失败发生在哪个环节？**

```
应用层: gt911_worker() → gt911_i2c_read()
  ↓
驱动层: r528_transfer() → hal_twi_xfer() → hal_twi_engine_do_xfer()
  ↓
硬件层: TWI 控制器 → I2C 总线 → GT9271 芯片
```

**关键判断：** 如果第一次读取成功、后续读取失败，而两次走完全相同的代码路径，那么问题**不在驱动层**（否则两次都应该失败）。问题在**芯片状态**或**硬件环境变化**。

### 第二层：用诊断代码捕捉瞬态

静态分析（读代码）只能告诉你"可能发生什么"。诊断代码告诉你"实际发生了什么"。

**诊断插入位置的铁律：**
- 必须在**故障发生的精确时刻**读取寄存器
- 不要在错误处理之后读（soft_reset 已经改变了状态）
- 不要在函数入口读（那时故障还没发生）

**本项目的关键诊断：**
```
hal_twi_engine_do_xfer():
  sem_wait()  ← 等中断
  [ENG_RES]   ← 在这里读！故障刚发生，状态未被篡改
  soft_reset  ← 这之后状态就变了
```

这个诊断位置揭示了 `msgs_idx=32` (SLA+NACK)，直接指向 GT9271 芯片本身。

### 第三层：接受芯片的行为模式

有些芯片行为没有"原因"，只有"模式"。GT9271 的行为模式：

```
上电 → 第一次 I2C 通信 → NACK
  ↓ 重置
第二次 I2C 通信 → ACK，之后全部正常
```

这不是 bug，是 GT9271 的初始化特性。Linux 内核的 goodix 驱动通过 probe 流程（读 config、设置中断等）自然地消耗了这个"第一次失败"。我们的 NuttX 驱动第一次读是 detect（成功），第二次读是 worker（失败），恰好踩中了这个边界。

## 心态纪律

### 规则 1: 不要用"常识"否定实验数据

```
❌ "RST 加上拉应该能稳定芯片" → 实验结果：无效
❌ "500ms 延迟应该让芯片稳定" → 实验结果：无效
✅ "实验表明上拉和延迟都无效，根因是芯片行为，不是电气环境"
```

### 规则 2: 一次只改一个变量

同时改多个东西，你不知道哪个有效。
- ❌ 同时加上拉 + 加延迟 + 改重置时序
- ✅ 先只加上拉 → 无效 → 去掉上拉只加延迟 → 无效 → 去掉延迟只加重置

### 规则 3: 修复要在最简单的层面

GT9271 需要两次重置。最简单的修复：
```c
if (read 失败) {
    gt911_reset_chip();  // 重置
    gt911_i2c_read();    // 重试
}
```

不需要改 TWI 驱动，不需要改 HAL，不需要改硬件。**在应用层用最少的代码解决问题。**

### 规则 4: 诊断代码不是永久代码

诊断代码的使命是**回答问题**。一旦问题回答完毕，立刻清除。留着只会：
- 增加代码体积
- 污染日志输出
- 让下一个人以为是功能代码

## LVGL Demo 思考方式

### 原则：先跑通再优化

1. **先让 Touch Test 跑起来** — 一个矩形 + 触摸变色 = 最小验证
2. **再加菜单** — 用按钮切换 Demo
3. **最后加内置 Demo** — Widgets / Music 是现成的，只需要正确调用 API

### 坑点记录

- `lv_color_make()` 不是 C 常量表达式，不能用于 static 数组初始化 → 用 `lv_color_hex()` + 运行时赋值
- `int32_t` 在 `printf` 中要用 `%ld` + `(long)` 强转，否则 `-Wformat` 报错
- `lv_nuttx_uv_loop()` 是本地 helper 函数，不是 LVGL API，需要保留在源码中

## NXPlayer 思考方式

### 问题：如何让播放器自动播放指定文件

NXPlayer 是交互式 shell（REPL），不接受命令行参数。有三个选择：

1. **修改源码支持参数** — 改 `main()` 加 `argc/argv` 解析 (✅ 采用)
2. **用脚本/管道** — `echo "play file" | nxplayer` — 需要 `NSH_PIPELINE`，未启用
3. **写 wrapper** — 新建一个小程序调用 `nxplayer_playfile()` API — 过度工程

选择原则：**改最少的代码达到目的。** 在 `main()` 开头加 20 行 if 判断就够了。

## 教训

### 教训 1: 驱动层"成功"不代表芯片层"就绪"

`gt911_control_initialize()` 中的 detect 读取（0x8140）成功，只说明 I2C 总线通了、芯片能响应。不代表芯片已经准备好接收后续的坐标读取命令。GT9271 可能在 detect 之后需要额外的初始化时间或状态转换。

### 教训 2: 上拉电阻不是万能药

I2C 上拉解决的是**信号完整性**问题（上升沿太慢、电平不够高）。GT9271 的 NACK 不是信号完整性问题——芯片**确实收到了地址**，只是**选择不应答**。这是协议层行为，不是电气层问题。

### 教训 3: INT 上拉会干扰通信

INT 引脚在 GT9271 中有复用功能。给 INT 加上拉改变了引脚默认电平，可能触发了 GT9271 的某种模式切换或地址变更（两个地址都 NACK 了）。**教训：不要随意改动数据手册没说可以改的引脚。**

### 教训 4: "500ms 什么都修不了"

在嵌入式系统中，`usleep(500000)` 是一个巨大的时间。如果问题在 500ms 内没自动修复，加更多延迟也不会修复。真正的修复必须是**主动的**（重置、重试、重新初始化），不是**被动的**（等一等）。

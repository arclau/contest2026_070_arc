# 项目记忆体系

适用工程 `/data/dm`。重点是让下次会话找到当前事实和可执行下一步，不靠增加必读文件解决失忆。

| 文档 | 唯一职责 |
|---|---|
| 根 `AGENTS.md` | 短入口、约束、任务路由、默认续接点；≤8KB |
| 根 `devlog.md` | 事件索引；≤40 节点、单行≤120字符 |
| `project_docs/ROADMAP.md` | 产品里程碑与阻塞，不重复实验细节 |
| `project_docs/devlogs/` | 各任务事实、实验、验证和补丁去留 |
| `project_docs/specs/` | 现行设计/流程；按任务读取 |
| `project_docs/methodology.md` | 排障记录格式与停止条件 |
| `project_docs/archive/` | 只供回溯，不作为当前操作指令 |

## 审查方法

1. 先对照实际脚本/源码，找出文档中的错误路径、反向同步、目标混用、失效完成标准。
2. 把观察、假设、结论分开；旧日志改结论时保留原始记录与校正日期。确认某次试验无效不等于排除整个模块。
3. 同一规则保留一个规范源，其他入口用链接；不要把完整构建命令、状态和仪式复制到每个 skill。
4. 状态按证据标明代码已实现/构建通过/运行待验；“完成”必须有验收范围。索引保持简短，用参考链接避免长行。
5. skill 必须与当前工程一致；旧示例不得覆盖用户授权或引导另建源码副本。
6. 更新后检查链接、主从导出与长度；按真实任务场景演练：仅文档、模拟器崩溃、板端资源交付各应走不同验证路径。

会话收尾规则见 `project_docs/specs/misc/development-workflow.md`。不要以 tag 数/文档数量证明效率；记录复现是否稳定、实验是否缩小范围、交付证据是否完整。
